# Feedbacks — registro único e testes de regressão
Atualizado em 29/09/2026. Ler antes de produzir e antes de fechar. Preferências vigentes no MEMORY.md da raiz; aqui ficam **problema, caso e comportamento que não pode regredir**. Não apagar feedback ao corrigir um card. Corrigido localmente não significa resolvido em todo o acervo.

## Como registrar
Uma entrada com ID estável, data, escopo, pedido literal quando disponível, exemplo/identidade, ação esperada, evidência de verificação e estado. Comentário de Anki é entrada mesmo sem cor. Remoção intencional pelo usuário encerra o alvo como removido, nunca autoriza recriação.
Estados: pendente → tratado na execução X → verificado; generalização permanece ativa. Preferência vigente muda no MEMORY, procedimento em EXECUCAO-DECK-AULA; não criar blocos de override ou documentos concorrentes.

### Todo feedback, recebido por qualquer executor

**Quem recebe registra nesta mesma sessão, antes de encerrar ou passar à próxima aula.** Vale para Codex e Claude, mensagem no chat, resposta a questionário, comentário no Anki, aprovação, rejeição e ajuste de um único card. Não guardar só feedback “generalizável”. Não pedir que Davi repita para a outra IA. Se o registro for interrompido, a retomada começa por reconciliar o que ficou pendente.

Registrar: origem/executor/data → fala literal (ou declarar resumo) → aula/card/versão, quando aplicável → alcance local ou geral → entendimento e eventual dúvida → ação/critério afetado → estado/evidência. “Pelo que vi por cima” não vira aprovação integral; ausência de crítica não vira aceite. Feedback novo não precisa esperar encerramento da UC para entrar nas próximas decisões. Não marcar verificado só porque mudou um documento.

Para novas entradas, usar `F-AAAAMMDD-CODEX-NN` ou `F-AAAAMMDD-CLAUDE-NN`, conferindo existência antes de gravar. IDs históricos permanecem; colisão é desambiguada com a origem preservada. Reler o trecho vivo antes de editar; alterações pontuais, sem regravar de memória o arquivo inteiro e apagar registros concorrentes. Não usar o lock de escrita do Anki para esperar respostas ou editar documentação.

Depois de registrar: atualizar a preferência no MEMORY em seu lugar, procedimento no roteiro técnico se necessário, estado da aula na fila e evidência na corrida. Q009/Q092/Q094: aplicar o aprendizado nas próximas entregas; alterar deck anterior somente se Davi pedir. Não criar handoff ou outra lista de regras. Na entrada **e antes de fechar** uma aula, reler feedbacks acrescentados pela outra sessão e registrar os IDs efetivamente considerados. Uma dúvida nova relevante recebe exemplos; avaliar cobertura médica e número de verdes é trabalho do executor, não uma pergunta a transferir ao estudante.

Este protocolo vale para sessões com acesso ao projeto compartilhado. Não existe coleta automática de conversas privadas de outra sessão ou computador: o executor que recebeu precisa persistir o feedback. Troca de máquina exige a versão atual dos documentos; arquivos de cards/recibos privados ignorados pelo Git não substituem memória de preferências portável. Não enviar/publicar dados para sincronizar por inferência.
